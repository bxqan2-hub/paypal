半自动支付编排系统技术设计

—— 结合提链（Paylink Extraction）与 Stripe 协议支付自动化 ——

在 SaaS 订阅支付领域，存在两条技术路线：一条是「提链」（Paylink Extraction），通过修改地区和币种参数，从 Stripe Checkout Session 中提取 UPI、PIX、iDEAL 等本地支付方式的跳转链接，让用户手动扫码付款；另一条是「协议支付自动化」，通过 HAR 抓包逆向 Stripe 内部接口，用纯 HTTP 请求模拟浏览器行为，全自动完成信用卡扣款。

这两条路线各有不可替代的价值，也各有无法逾越的边界：

- 提链能激活各国本地支付通道，但原生流程止步于「输出跳转链接」，后续付款和结果确认必须由人工完成，无法规模化批量处理。
- 协议支付能全自动完成扣款，但原生只支持银行卡（card）支付方式，无法直接调用 UPI、PIX、MoMo 等强依赖客户端交互的本地支付。
本文设计的「半自动支付编排系统」，正是将两者结合：用提链技术完成账号侧结账和跨区会话创建，用协议支付技术完成 Stripe 侧的自动化执行，对支持全自动的支付方式（信用卡、Stripe Link）走无人值守通道，对必须人工介入的支付方式（UPI、PIX、Kakao Pay 等）输出链接并在人工完成后自动轮询确认结果。整个系统从账号结账到支付结果确认形成闭环。

【免责声明】本文为技术架构设计与原理分析，所有接口细节基于 Stripe Checkout 协议逆向研究。逆向调用厂商未公开接口可能违反服务条款，实际使用存在账号封禁、资金损失等风险，仅供学习研究。

## 一、系统整体架构与设计理念

### 1.1 设计目标

半自动支付编排系统的核心设计目标是「能自动的全自动，不能自动的最小化人工介入」：

- 统一入口：所有支付请求从同一个编排器进入，不管最终走卡支付还是本地支付
- 智能路由：根据支付方式类型自动判断走全自动通道还是人工介入通道
- 闭环确认：无论哪条通道，最终都由系统统一确认支付结果并更新订阅状态
- 可观测性：每一步状态可追踪、可重试、可审计
### 1.2 五大核心模块

系统由五个核心模块组成，各司其职又紧密协作：

### Table 0

| 模块 | 职责 | 技术来源 |
| --- | --- | --- |
| A. 账号结账层 | 登录态管理、创建跨区 Checkout Session、税务地址更新 | 提链技术 |
| B. 支付路由引擎 | 根据 payment_method_types 决策走全自动还是人工通道 | 编排层新增 |
| C. 协议支付执行器 | ConfirmationToken 创建、PaymentIntent 确认、3DS 处理 | 协议支付技术 |
| D. 人工介入通道 | 生成支付链接/二维码、通知用户、等待回调 | 提链技术 + 编排层 |
| E. 结果确认状态机 | 统一轮询/回调确认、状态流转、失败重试 | 两者结合 |

【架构要点】关键设计：模块 B（支付路由引擎）是整个系统的「大脑」。它在模块 A 创建完 Checkout Session 后，读取返回的 payment_method_types 字段，根据支付方式的自动化可行性做出路由决策——这是半自动系统区别于纯提链或纯协议支付的核心。

### 1.4 半自动的含义

「半自动」不是「一半自动一半手动」的模糊概念，而是有明确定义的分流机制：

### Table 1

| 支付方式类型 | 处理模式 | 人工介入点 | 结果确认方式 |
| --- | --- | --- | --- |
| 信用卡 (card) | 全自动 | 无 | PaymentIntent 状态 = succeeded |
| Stripe Link 钱包 | 全自动 | 无 | PaymentIntent 状态 = succeeded |
| iDEAL / BLIK / GCash | 半自动 | 用户打开链接完成银行/App确认 | 轮询 PaymentIntent / Stripe 回调 |
| UPI / PIX / TWINT | 半自动 | 用户扫码或输入VPA完成支付 | 轮询 PaymentIntent / Stripe 回调 |
| Kakao Pay / MoMo | 半自动(需pre_confirm) | 用户在App内确认 | 轮询 + pre_confirm 状态跟踪 |

## 二、模块 A：账号结账与会话创建（提链层）

模块 A 负责从账号登录态出发，创建一个带有目标地区和币种的 Stripe Checkout Session。这是整个支付流程的起点，也是提链技术的核心价值所在——绕过平台前端限制，激活 Stripe 原生支持的本地支付方式。

### 2.1 登录态与 Access Token 获取

系统首先需要有效的平台账号登录态。以 ChatGPT 为例：

# 方式1：从已登录浏览器的 session cookie 换取
GET https://chatgpt.com/api/auth/session
→ {"accessToken": "eyJhbGciOiJSUzI1NiIs...", "user": {...}}

# 方式2：直接使用 __Secure-next-auth.session-token cookie
# 系统内部维护 cookie jar，自动刷新 access token（有效期5~10分钟）

编排系统需要维护一个账号池，每个账号独立存储 session token，并在 token 即将过期时自动刷新。

### 2.2 创建跨区 Checkout Session

使用 Access Token 调用平台结账 API，关键是通过 billing_details 指定目标国家和币种：

POST https://chatgpt.com/backend-api/payments/checkout
Authorization: Bearer {access_token}

{
  "entry_point": "all_plans_pricing_modal",
  "plan_name": "chatgptplusplan",
  "billing_details": {
    "country": "NL",       // 目标国家：NL=荷兰, IN=印度, BR=巴西...
    "currency": "EUR"      // 目标币种：EUR, INR, BRL...
  },
  "checkout_ui_mode": "custom"
}

响应中的关键字段：

{
  "checkout_session_id": "oaics_xxxxxxxxxxxx",
  "publishable_key": "pk_live_xxxxxxxxxxxx",
  "payment_method_types": ["card", "ideal"]   // ← 路由引擎的决策依据
}

【架构要点】payment_method_types 是模块 B 路由决策的核心输入。传 NL+EUR 返回 ["card", "ideal"]，传 IN+INR 返回 ["card", "upi"]，传 BR+BRL 返回 ["card", "pix"]。不同的国家/币种组合激活不同的本地支付方式。

### 2.3 税务地址优化

创建 Session 后，需要更新税务地址。使用美国免税州（Oregon、Montana、Delaware、New Hampshire、Alaska）地址可以消除 VAT 消费税：

POST /api/v1/payments/checkout/taxes
{
  "checkout_session_id": "oaics_xxx",
  "billing_details": {
    "name": "John Doe",
    "address": {
      "country": "US", "state": "OR",
      "city": "Portland", "postal_code": "97201",
      "line1": "123 Main St"
    }
  }
}
→ {"snapshot": {"amount_total": 2000, "currency": "eur"}}

【关键】taxes 响应中的 amount_total 是后续 Confirm 请求 expected_amount 的准确来源。如果用 Init 步骤的金额去 Confirm，可能因税后金额不一致而失败。税务地址必须与后续 ConfirmationToken 中的地址保持一致。

### 2.4 Stripe Session 初始化与状态管理

提链的完整协议流程包含 12 步，编排系统需要严格按顺序执行并维护会话状态：

1.  Session Refresh      — cookie 换新的 Access Token
2.  Create Checkout      — 创建 oaics_ / cs_live_ session
3.  Stripe Init          — POST payment_pages/{id}/init，获取 ppage_token
4.  Update OAI Taxes     — 通知平台更新税务地址
5.  Stripe Tax Region    — 更新 Stripe 侧税务区域
6.  Stripe Customer Data — 更新客户信息
7.  Checkout Snapshot    — 保存 checkout 快照（获取 amount_total）
8.  Pre-Confirm          — Kakao Pay / MoMo 必须（其他支付方式跳过）
9.  Create Payment Method— 创建 PM，类型 = card/ideal/upi/pix...
10. Confirm              — 确认支付，触发重定向或扣款
11. Approve              — Hosted 模式需要（Sentinel Token）
12. Extract Result       — 提取 redirect_url 或 PaymentIntent 状态

每一步响应中都会更新 eid（element ID）、mrid（merchant reference ID）等会话状态字段，下一步必须携带最新值。这意味着 12 步必须严格串行，不能并行。

### 2.5 提链层的五个经典坑

### Table 2

| 坑点 | 现象 | 解决方案 |
| --- | --- | --- |
| IP 一致性 | 创建和确认用不同IP → invalid_request_error | 整个12步绑定同一个出口IP，HTTP client 不切换 |
| expected_amount | Confirm金额与Session不一致 → 拒绝 | 从 taxes 响应的 snapshot.amount_total 取值 |
| Session State | 跳过步骤或用旧eid/mrid → 后续报错 | 严格按顺序执行，每步更新状态字段 |
| Accept-Language / guid | 缺header或guid格式错 → 非预期响应 | 必传 Accept-Language，guid用UUID+6位hex=42字符 |
| 超时 | Confirm后无redirect_url → 卡住 | 轮询init接口，最多等90秒，超时标记失败 |

## 三、模块 B：支付方式路由与决策引擎

模块 B 是半自动编排系统的核心决策层。它在模块 A 完成 Checkout Session 创建后，根据 payment_method_types 和系统配置，决定当前交易走哪条执行通道。

### 3.1 路由决策逻辑

def route_payment(checkout_session, config):
    pm_types = checkout_session["payment_method_types"]
    preferred = config.get("preferred_method", "card")

    # 优先级1：用户指定的支付方式
    if preferred in pm_types:
        selected = preferred
    # 优先级2：优先选可全自动的卡支付
    elif "card" in pm_types and config.allow_card_auto:
        selected = "card"
    # 优先级3：回退到第一个本地支付方式
    else:
        selected = pm_types[-1]  # 最后一个通常是本地支付

    # 决策：是否可全自动
    if selected in ("card", "link"):
        return {"channel": "auto", "method": selected}
    else:
        return {"channel": "manual", "method": selected}

| 支付方式 | PM Type | 国家 | 自动化可行性 | 需pre_confirm | 人工操作 |
| --- | --- | --- | --- | --- | --- |

| Stripe Link | link | 全球 | 全自动 | 否 | 无 |
| iDEAL | ideal | 荷兰 | 半自动 | 否 | 银行选择页确认 |
| UPI | upi | 印度 | 半自动 | 否 | VPA输入/扫码确认 |
| PIX | pix | 巴西 | 半自动 | 否 | 扫码支付 |
| TWINT | twint | 瑞士 | 半自动 | 否 | App跳转确认 |
| Kakao Pay | kakao_pay | 韩国 | 半自动 | 是 | Kakao App确认 |
| BLIK | blik | 波兰 | 半自动 | 否 | 6位码输入 |
| MoMo | momo | 越南 | 半自动 | 是 | MoMo App确认 |
| GCash | gcash | 菲律宾 | 半自动 | 否 | GCash确认页 |

### 3.3 路由策略配置

编排系统支持多种路由策略，适应不同业务场景：

- 成本优先：优先选择费率最低的支付方式（通常本地支付费率低于信用卡）
- 速度优先：优先选择全自动通道（card/link），跳过人工等待
- 地区优先：根据账号注册地或代理IP所在地自动匹配对应本地支付
- 手动指定：运营人员在任务创建时明确指定支付方式
【架构要点】路由引擎的输出是一个标准化的 PaymentTask 对象，包含 channel（auto/manual）、method（支付方式类型）、session_id、publishable_key、expected_amount 等字段。后续模块 C 和 D 都基于这个对象执行，不需要关心上游是怎么创建 Session 的。

## 四、模块 C：协议支付自动执行器（卡类全自动通道）

当路由引擎判定走 auto 通道时，模块 C 接管后续流程。它基于 Stripe 协议支付自动化技术，用纯 HTTP 请求模拟浏览器完整操作链路，在无 GUI 环境下完成从卡号令牌化到扣款成功的全流程。

### 4.1 Custom 模式执行流程（oaics_）

Custom 模式是最干净的全自动路径，共 4 个核心步骤：

Step 1: 获取 Elements Session 配置
GET /v1/elements/sessions?deferred_intent[mode]=subscription
  &deferred_intent[amount]={amount}&deferred_intent[currency]={currency}
  &type=deferred_intent&key={pk_live}&_stripe_version=2025-03-31.basil
→ elements_session_id, customer_session_client_secret, pmc_xxx

Step 2: 创建 ConfirmationToken（卡号 → ctoken_）
POST /v1/confirmation_tokens
  type=card
  payment_method_data[card][number]=...
  payment_method_data[card][exp_month]=...
  payment_method_data[card][exp_year]=...
  payment_method_data[card][cvc]=...
  payment_method_data[billing_details][address][country]=US
  key={pk_live}&_stripe_version=2025-03-31.basil
  + guid/muid/sid 指纹参数（42字符格式）
→ {"id": "ctoken_1xxx"}

Step 3: 平台侧确认
POST /api/v1/payments/checkout/confirm
  {"checkout_session_id": "oaics_xxx", "confirmation_token": "ctoken_1xxx"}
→ {"client_secret": "pi_xxx_secret_xxx"}

Step 4: Stripe 侧扣款
POST /v1/payment_intents/{pi_id}/confirm
  confirmation_token=ctoken_xxx
  client_secret=pi_xxx_secret_xxx
  return_url=...
  key={pk_live}&_stripe_version=2025-03-31.basil
  client_attribution_metadata[merchant_integration_source]=l1
→ {"status": "succeeded"} 或 {"status": "requires_action"}

### 4.2 Hosted 模式执行流程（cs_live_）

Hosted 模式流程更长，涉及 Payment Page 初始化和 Approve 机制：

Step 1: Payment Page 初始化
GET /api/payment-page/{cs_live_xxx}/init
→ {"ppage_token": "ppage_xxx"}

Step 2: Elements Session（带 Hosted 特殊字段）
POST /v1/elements/sessions
  checkout_session_id=cs_live_xxx
  elements_init_source=custom_checkout
  _stripe_version=2025-03-31.basil; checkout_server_update_beta=v1; ...
→ passive_captcha.rqdata（hCaptcha Enterprise 参数）

Step 3: 创建 ConfirmationToken（同 Custom）

Step 4: Payment Pages Confirm
POST /v1/payment_pages/{cs_live_xxx}/confirm
  elements_session_client[...] = ...（8个子字段）
  init_checksum / js_checksum / rv_timestamp（动态提取）
  expected_amount = {amount}
→ {"status": "open", "requires_approval": true}

Step 5: 等待平台自动 Approve（fall-through）
  或手动 Approve（需 Sentinel Token + Turnstile 验证）

Step 6: 轮询 Payment Page 状态
POST /v1/payment_pages/{cs_live_xxx}/poll
→ payment_object_status: open / requires_action / succeeded

### 4.3 3DS / hCaptcha 挑战处理

当 PaymentIntent 进入 requires_action 状态时，需要处理 Stripe 自有的 hCaptcha Enterprise 挑战：

POST /v1/payment_intents/{pi_id}/verify_challenge
  captcha_response={hcaptcha_token}      # P0开头的长字符串
  captcha_vendor_name=hcaptcha
  captcha_sitekey={sitekey}              # 从 elements_session 提取
  expected_amount={amount}
  expected_currency={currency}
  key={pk_live}
  client_secret={pi_secret}

hCaptcha Enterprise 的特殊性：

- 必须携带 rqdata 参数（从 elements_session.passive_captcha 提取）
- sitekey 是 Stripe 专有，不是通用 hCaptcha sitekey
- invisible 模式，浏览器中看不到验证码图片
- token 时效性强（浏览器 ~4 秒解出有效，远程打码需 30-120 秒）
【重要澄清】重要澄清：Stripe 的 verify_with_challenge 并非传统银行 3DS 验证。它是 Stripe 自有的风控挑战，使用 hCaptcha 作为人机验证手段。真正的银行 3DS（Visa Secure）会打开银行页面要求 OTP，纯协议无法绕过。但虚拟信用卡通常只触发 Stripe hCaptcha，不触发银行 3DS。

### 4.4 Fast-Path 优化

有时 confirm 返回 requires_action，但 PI 实际上已经扣款成功。正确做法是先查询 PI 状态：

pi = stripe.get(f"/v1/payment_intents/{pi_id}", key=pk_live)
if pi["status"] == "succeeded":
    return SUCCESS  # 已扣款成功，跳过 captcha
elif pi["status"] == "requires_action":
    solve_hcaptcha(pi)  # 确实需要验证

### 4.5 拒卡分类与重试

### Table 4

| 错误码 | 分类 | 处理策略 |
| --- | --- | --- |
| generic_decline | 可重试 | 换卡重建 ConfirmationToken，同一PI重试 |
| insufficient_funds | 可重试 | 充值或换卡后重试 |
| processing_error | 可重试 | Stripe侧临时错误，直接重试 |
| stolen_card / lost_card | 不可重试 | 卡已标记，从卡池移除，放弃session |
| card_not_supported | 不可重试 | 卡类型不支持，换卡 |
| currency_not_supported | 不可重试 | 卡不支持目标币种，换卡或换地区 |
| incorrect_cvc | 特殊处理 | 检查CVC是否传错 |
| expired_card | 特殊处理 | 卡过期，从卡池移除 |
| card_velocity_exceeded | 特殊处理 | 交易频率超限，冷却后重试 |

【架构要点】同一个 PaymentIntent 被拒卡后，可以用新的 ConfirmationToken 重试，不需要重建整个 Checkout Session。这大幅提升了批量支付的效率——换卡只需要重新执行 Step 2 和 Step 4。

## 五、模块 D：人工介入通道（本地支付扫码）

当路由引擎判定走 manual 通道时，模块 D 接管。它的职责是：从提链流程的 Confirm 响应中提取支付跳转链接，以可操作的形式（URL/二维码）交付给用户，并在用户完成支付后将控制权交回模块 E 进行结果确认。

### 5.1 提取支付链接

提链流程的第 10 步 Confirm 之后，对于重定向类型的支付方式，Stripe 返回：

{
  "status": "requires_action",
  "next_action": {
    "type": "redirect_to_url",
    "redirect_to_url": {
      "url": "https://hooks.stripe.com/redirect/authenticate/src_xxx?client_secret=..."
    }
  }
}

这个 redirect_url 就是最终支付链接。不同支付方式打开后的页面不同：

- iDEAL → 银行选择页，用户选银行后跳转网银确认
- UPI → VPA 输入页或二维码，用户在 UPI App 中确认
- PIX → 二维码页面，用户用巴西银行App扫码
- Kakao Pay → Kakao 确认页，用户在 KakaoTalk 中确认
- MoMo → MoMo App 跳转，用户在 App 内确认支付
### 5.2 Kakao Pay / MoMo 的 pre_confirm 特殊处理

Kakao Pay 和 MoMo 需要额外的 pre_confirm 调用，否则 Confirm 返回 incomplete 状态，拿不到 redirect_url：

POST /v1/payment_pages/{oaics_xxx}/pre_confirm
Content-Type: application/x-www-form-urlencoded
expected_payment_method_type=kakao_pay

【容易踩坑】如果不知道有 pre_confirm 这一步，Kakao Pay 和 MoMo 的提链会卡在最后一步——所有参数都对，就是拿不到链接。这类细节只有通过 HAR 抓包完整结账流程才能发现。

### 5.3 链接交付与用户通知

编排系统需要将支付链接以用户可操作的方式交付：

PaymentLink {
  task_id: "pay_20260829_001",
  method: "upi",
  redirect_url: "https://hooks.stripe.com/redirect/authenticate/src_xxx?...",
  qr_code: <base64_png>,           // 系统自动生成二维码
  amount: "₹1,950",
  currency: "INR",
  expires_in: 900,                 // 链接有效期（秒）
  created_at: "2026-08-29T12:00:00Z"
}

交付方式可以是：Web 管理面板展示、API 回调通知、消息推送等。系统同时生成二维码，方便手机扫码支付。

### 5.4 人工支付超时管理

本地支付链接通常有有效期（一般 15 分钟），系统需要管理超时：

- 链接生成后启动倒计时，默认 15 分钟
- 超时未支付 → 标记任务为 TIMEOUT，释放卡池/代理资源
- 用户支付后但系统未检测到 → 延长轮询窗口（最多 30 分钟），防止网络延迟导致误判
- 超时后用户仍完成了支付 → 通过 Stripe 对账机制补单（webhook 回调）
### 5.5 半自动通道的人工介入最小化

虽然叫「人工介入通道」，但系统设计目标是将人工操作压缩到极致：

- 用户只需做一件事：打开链接（或扫码）→ 在支付App中点确认
- 不需要用户填写任何信息（金额、收款方都已由系统预设）
- 支付完成后不需要用户通知系统，系统自动轮询检测结果
- 用户甚至不需要知道背后是 Stripe，只看到一个支付页面
## 六、模块 E：支付结果确认与统一状态机

模块 E 是整个系统的闭环保障。无论走 auto 通道还是 manual 通道，最终都由模块 E 统一确认支付结果、更新订阅状态、处理异常。

### 6.1 统一支付状态模型

### Table 5

| 状态 | 含义 | 触发条件 | 后续动作 |
| --- | --- | --- | --- |
| PENDING | 任务已创建，等待执行 | 路由引擎分配通道 | 进入模块C或D |
| PROCESSING | 支付执行中 | 协议执行器/提链流程运行中 | 等待Confirm结果 |
| AWAITING_PAYMENT | 等待用户付款 | manual通道已输出链接 | 启动轮询+超时计时 |
| REQUIRES_ACTION | 需要验证挑战 | auto通道触发hCaptcha/3DS | 打码处理或转人工 |
| SUCCEEDED | 支付成功 | PI状态=succeeded | 激活订阅，记录结果 |
| FAILED | 支付失败 | 拒卡/超时/异常 | 分类重试或标记终态 |
| TIMEOUT | 支付超时 | manual通道超期未付 | 释放资源，可重新创建 |
| REFUNDED | 已退款 | Stripe退款回调 | 取消订阅，记录 |

### 6.2 Auto 通道的结果确认

全自动通道的结果确认相对直接：

# Step 4 (payment_intents/confirm) 响应
if response["status"] == "succeeded":
    → SUCCEEDED，激活订阅
elif response["status"] == "requires_action":
    → 先查PI真实状态（Fast-Path优化）
    → 若已succeeded → SUCCEEDED
    → 若确实requires_action → 解hCaptcha → 重新confirm
elif response["status"] == "requires_payment_method":
    → 拒卡，分类处理（换卡重试/放弃）

### 6.3 Manual 通道的结果确认

人工通道的结果确认是半自动系统最关键的环节。用户在外部完成支付后，系统需要主动检测到支付成功：

# 轮询策略（推荐）
def poll_payment_result(pi_id, max_wait=1800):
    # 每3秒轮询一次PaymentIntent状态，最多等30分钟
    for elapsed in range(0, max_wait, 3):
        pi = stripe.get(f"/v1/payment_intents/{pi_id}", key=pk_live)
        if pi["status"] == "succeeded":
            return SUCCEEDED
        elif pi["status"] == "canceled":
            return FAILED
        elif pi["status"] == "requires_payment_method":
            return FAILED  # 用户取消了支付
        sleep(3)
    return TIMEOUT

除了主动轮询，系统还应支持 Stripe Webhook 回调作为补充确认渠道：

- payment_intent.succeeded → 支付成功，激活订阅
- payment_intent.payment_failed → 支付失败，记录原因
- charge.refunded → 已退款，取消订阅
【架构要点】轮询 + Webhook 双保险：轮询保证系统主动感知状态变化，Webhook 保证轮询间隔内的事件不丢失。两者通过 payment_intent id 去重，避免重复处理。

### 6.4 订阅激活确认

Stripe 侧支付成功不等于平台订阅已激活。系统还需要确认平台侧的订阅状态：

# 支付成功后，验证平台侧订阅状态
GET /api/v1/me/subscription
→ {"subscription": {"plan": "plus", "status": "active", "renews_at": "..."}}

# 如果平台侧未激活（Stripe回调延迟），继续轮询平台API
# 最多等 60 秒，通常 Stripe webhook 会在几秒内通知平台

### 7.3 并发批量处理

编排系统支持批量任务处理，通过信号量控制并发：

- manual 任务的结果确认与 auto 任务的执行并行进行
## 八、风控基础设施

无论是提链还是协议支付，都面临 Stripe Radar 和平台侧的风控检测。编排系统需要一套统一的风控基础设施，为所有通道提供指纹伪装、代理管理和行为模拟。

### 8.1 TLS 指纹管理

Stripe 和 Cloudflare 会检查 TLS Client Hello 指纹（JA3/JA4），不匹配浏览器特征直接返回 403/429。

# Python 使用 curl_cffi 模拟浏览器 TLS 指纹
from curl_cffi import requests

PROFILES = [
    {"tls": "chrome131", "ua": "Mozilla/5.0 ... Chrome/131.0.0.0",
     "sec_ch_ua": '"Not=A?Brand";v="99", "Chromium";v="131"'},
    {"tls": "safari18", "ua": "Mozilla/5.0 ... Safari/605.1.15",
     "sec_ch_ua": None},
    {"tls": "firefox117", "ua": "Mozilla/5.0 ... Firefox/117.0",
     "sec_ch_ua": None},
]

# 遇到403/429时自动轮换指纹，最多重试3次

【一致性要求】TLS 指纹必须与 User-Agent 成对匹配。用 Chrome 131 的 TLS 指纹但 UA 写 Chrome 124，会被 Cloudflare bot detection 立即发现。

### 8.2 Stripe.js 设备指纹

所有 Stripe API 请求需要携带设备指纹参数：

### Table 7

| 参数 | 格式 | 作用 |
| --- | --- | --- |
| guid | UUID + 6位hex = 42字符 | 全局唯一标识 |
| muid | 同 guid 格式 | 设备标识 |
| sid | 同 guid 格式 | 会话标识 |
| time_on_page | 随机8-30秒 | 模拟真实用户停留时间 |
| _stripe_version | 从deploy_status动态提取 | API版本号 |

此外，建议在业务请求前向 m.stripe.com/6 发送至少一次指纹注册（stripejs-init-complete），降低 Radar 异常检测风险。r.stripe.com/b 遥测上报为纯可选。

### 8.3 双代理池架构

┌─────────────────────────────────────┐
│           代理池管理器               │
│                                     │
│  ┌──────────────┐  ┌──────────────┐ │

│  │ (匹配账号地区) │  │ (住宅IP优先)  │ │

### Table 8

| 代理类型 | 适用场景 | 风险等级 |
| --- | --- | --- |
| 住宅代理 (Residential) | Stripe API / 平台 API | 最低，推荐生产 |
| ISP静态住宅代理 | 长期固定使用 | 中等，部分已被标记 |

【铁律】出口 IP 一致性是铁律：创建 Checkout Session 和确认支付必须使用同一个出口 IP。Stripe 会比对两次请求的 IP，不一致直接拒绝交易。整个支付流程（提链12步 + 协议支付）必须绑定同一个代理出口。

### 8.4 请求节奏模拟

纯协议支付的风险是请求速度太快。浏览器用户从打开支付页面到点击确认通常需要 15-60 秒，自动化 2 秒完成会被 Radar 标记。

# 关键步骤间加入随机延迟
await sleep(random.uniform(1.5, 3.0))   # 创建 session 后
await sleep(random.uniform(0.8, 2.0))   # 更新税务后
await sleep(random.uniform(1.0, 2.5))   # 创建 token 后
await sleep(random.uniform(0.5, 1.5))   # confirm 前
# 总时间控制在 8-30 秒之间比较自然

### 8.5 Cookie 隔离

使用两个独立的 HTTP 客户端，严格隔离平台 Cookie 和 Stripe Cookie：

- 平台客户端：带 session token cookie，用于调用平台 API
- Stripe 客户端：不带任何 cookie，用于调用 api.stripe.com
- 绝不允许 Stripe 客户端发送平台 Cookie，反之亦然
## 九、异常处理与重试策略

支付流程中任何一步都可能失败。编排系统需要一套完善的异常分类和重试机制，确保可恢复的错误自动恢复，不可恢复的错误清晰上报。

### 9.1 异常分类矩阵

### Table 9

| 异常类型 | 典型表现 | 可重试 | 处理策略 |
| --- | --- | --- | --- |
| 网络瞬断 | ConnectionError / Timeout | 是 | 退避重试，最多3次 |
| 限流 (429) | Too Many Requests | 是 | 指纹轮换+指数退避 |
| TLS指纹被封 (403) | Forbidden | 是 | 切换TLS profile+代理 |
| IP不一致 | invalid_request_error | 否(本session) | 检查代理钉住，重建session |
| 拒卡 (generic_decline) | 卡被拒绝 | 是(换卡) | 换卡重建token，同PI重试 |
| 余额不足 | insufficient_funds | 是(换卡) | 换卡或充值后重试 |
| 卡被盗标记 | stolen_card | 否 | 移除卡池，放弃session |
| hCaptcha超时 | auth_failure | 是 | 换新captcha token重试 |
| manual超时 | 用户未支付 | 可重建 | 标记timeout，可重新创建任务 |
| Session过期 | session expired | 可重建 | 回到模块A重建session |
| Sentinel token无效 | approve返回blocked | 否(本session) | 重新生成Turnstile token |

### 9.2 退避重试策略

def with_retry(func, max_retries=3, base_delay=1.0):
    for attempt in range(max_retries):
        try:
            return func()
        except RateLimitError:
            # 429: 轮换指纹 + 指数退避
            tls_manager.rotate()
            sleep(base_delay * (2 ** attempt) + random.uniform(0, 1))
        except NetworkError:
            # 网络错误: 纯退避
            sleep(base_delay * (2 ** attempt))
        except TLSFingerprintBlocked:
            # 403: 换指纹 + 换代理
            tls_manager.rotate()
            proxy_pool.rotate()
            sleep(base_delay)
    raise MaxRetriesExceeded()

### 9.3 幂等性保证

重试机制必须保证幂等性，避免重复扣款：

- 每个支付任务有唯一 task_id，所有状态更新基于 task_id 做乐观锁
- PaymentIntent 确认使用 Idempotency-Key（Stripe 原生支持）
- manual 通道的链接生成是幂等的——同一 session 多次 confirm 返回相同的 redirect_url
- 订阅激活检查是幂等的——已激活的账号再次检查返回相同状态
### 9.4 死信队列与人工兜底

超过最大重试次数的任务进入死信队列（DLQ），由运营人员人工介入：

- DLQ 任务保留完整的执行日志、最后错误信息、已完成的步骤
- 运营可选择：重试、换支付方式、换账号、标记放弃
- 对于「钱已扣但订阅未激活」的异常状态，优先通过 Stripe 对账确认，避免误判
## 十、安全边界与最佳实践

### 10.1 Session 隔离

- 每次支付使用独立的 Checkout Session，不复用已失败的 Session
- Hosted 模式下 approve 操作后的 Session 不可再次使用
- 每个账号的支付任务独立运行，不共享 HTTP client、cookie jar、代理
### 10.2 Dry-Run 调试模式

所有实现应支持 Dry-Run 模式——执行完整流程但不提交最终的 confirm：

if config.commit_payments:
    result = stripe.confirm_payment_intent(pi_id, token)
else:
    logger.info("Dry-run: skipping confirm")
    result = {"status": "dry_run", "pi_id": pi_id}

Dry-Run 可以验证整个流程（创建 session、生成 token、税务计算、路由决策）都正确，而不实际扣钱。这对于调试新支付方式接入、新地区配置尤为重要。

### 10.3 敏感数据保护

- 信用卡号仅在内存中使用，支付完成后立即清除，不写入磁盘或日志
- Session token 在日志中用 *** 替代
- 代理凭据使用环境变量或加密存储，不硬编码
- Stripe Publishable Key 可写入代码（本来就是公开的），但 Secret Key 绝不能出现在客户端
- 支付链接中的 client_secret 有时效性，过期后自动失效
### 10.4 可观测性与审计

编排系统应记录完整的支付审计日志：

### Table 10

| --- | --- | --- |
| task_id | 支付任务唯一标识 | 永久 |
| account_id | 账号标识（脱敏） | 永久 |
| channel | auto / manual | 永久 |
| payment_method | card / upi / pix / ... | 永久 |
| amount / currency | 金额和币种 | 永久 |

### 10.5 与官方合规方案的边界

最后需要明确本系统与 Stripe 官方合规方案的边界：

### Table 11

| 维度 | 本编排系统（逆向协议） | Stripe 官方合规方案 |
| --- | --- | --- |
| 接口性质 | 逆向 Stripe 内部私有 API | 官方公开 API + SDK |
| 支付方式 | 可激活前端隐藏的本地支付 | 仅商户后台配置的支付方式 |
| 跨区定价 | 可通过 country/currency 参数切换 | 受商户配置限制 |
| 风控对抗 | 需要 TLS 指纹、代理、行为模拟 | 不需要，官方 SDK 自带 |
| 稳定性 | 依赖接口不变化，随时可能失效 | 有版本保障和迁移路径 |
| 合规性 | 可能违反 Stripe 服务条款 | 完全合规 |
| 适用场景 | 技术研究、特定场景自动化 | 生产环境商业支付 |

核心思路是：用提链激活跨区本地支付能力，用协议支付实现卡类全自动扣款，通过路由引擎分流，通过统一状态机关环。系统的价值不在于「绕过」什么，而在于将两种技术各自的优势组合起来，覆盖更广泛的支付场景，同时将人工介入压缩到最低限度。

【最终声明】本系统的设计基于对 Stripe Checkout 协议的逆向分析。Stripe 可能随时更新接口、版本号、风控策略，导致系统部分或全部失效。生产环境商业支付应使用 Stripe 官方 API 和 SDK。本文仅用于技术学习与架构设计参考。
